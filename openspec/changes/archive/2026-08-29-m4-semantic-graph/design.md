## Context

WebOps 的页面理解依赖语义图（§7/§8）：原始 DOM 对 LLM 不可靠且 token 昂贵。M4 模块需在 M1（浏览器驱动，提供 DOM 快照）与 M0（LLM 客户端）之上，把页面加工为结构化语义图，并输出 LLM 可读的层次树文本。工程约束：流程确定性、LLM 只在语义字段内行使有界执行权、每次生成无缓存以保证语义图始终正确反映当前页面。详见 `proposal.md` 的 Why 与 `docs/contract.md` §7/§8/§9.5。

## Goals / Non-Goals

**Goals:**
- 两阶段流水线解耦：程序化阶段（纯程序）与 LLM 填充阶段（每元素 purpose + related-to 打分）各自独立、可单独测试。
- 程序化阶段完全独立于 LLM 与浏览器真实环境（DOM 快照可 mock、HTML fixture 可驱动），保证可离线验证。
- `semantic_graph(page_ref, 范围, LOD)` 统一入口，LOD 四维参数组合实现清晰、可断言。
- 引擎内部对象模型与 LLM 序列化文本分层：对象模型承载机器校验/ref 映射/断言求值，序列化只为 LLM 可读性服务，互不耦合。
- ref 解析全确定性（引用归引擎，不信任 LLM），采用会话内即用即弃（方案 B）。

**Non-Goals:**
- 不做缓存/指纹/失效机制（§9.5 明确每次完整生成）。
- 不处理 iframe、懒加载/虚拟滚动/动态渲染、Canvas 渲染页面。
- 不做跨快照的身份跟踪与稳定 ref（方案 B 明确即用即弃）。
- 不承担定位/提取决策本身（那是 M6 叶子 agent 通过 M5 消费语义图的工作）。
- 不负责跨模块断言求值（留给消费方）。

## Decisions

### D1：两阶段流水线为模块内部边界，LLM 填充封装在可注入的填充器内

实现上把程序化阶段与 LLM 填充阶段分为两个内部阶段组件，LLM 填充器作为可注入依赖（`LlmFiller` 接口：`fill_purpose` + `score_related_to`）。测试时注入 mock 填充器返回固定 purpose/打分。

- 备选：将两阶段合并为一个函数，LLM 调用硬编码在生成流程内。缺点：无法独立测试程序化阶段，与验收标准"程序化阶段可独立测试（不依赖 LLM）"冲突。
- 理由：契约 §8.3 明确两阶段各司其职；注入边界同时满足 mock 测试与真实 M0 接入。

### D2：候选筛选以"语义容器层级"而非 DOM 深度为准

进图单位是元素，文本作为元素属性；语义容器（form/table/dialog/nav/section/fieldset/ul）作 REGION 骨架，纯定位 div/span 只用于归属判定（通过 DOM 祖先关系）。

- 备选 A：照搬 DOM 深度建层级。缺点：深而噪音多、烧 token、语义不清（契约 §8.4 明示层级=语义容器 vs DOM 深度）。
- 备选 B：全部元素进图再裁剪。缺点：中间 token 开销大，且裁剪逻辑复杂度不低于正向筛选。
- 理由：正向规则（必进/容器进/纯结构归属性/过滤隐藏）简单、可测试，与 §8.4 完全一致。

### D3：三种边由两种来源生成，related-to 语义部分交给 LLM

part-of/value-of 来自结构（DOM 树）与表格框架，程序化生成；related-to 的几何候选由程序化阶段按 bounds 邻近性预筛（作为候选输入，不直接成边），语义打分与理由由 LLM 每次生成时填充。

- 备选：规则给几何候选即视为边，LLM 不介入。缺点：规则无法可靠判断"标签-控件"语义对（契约 §8.5 已否决"规则优先、仅歧义时 LLM 兜底"）。
- 理由：程序化给候选、LLM 定语义与权重，符合"LLM 理解的产物，不是规则的廉价推断"。

### D4：LOD 实现为四维裁剪器组合，而非四个独立生成路径

深度（语义容器嵌套层数）、广度（候选集合大小）、属性（每个元素携带字段多少）、关联（related-to 边详尽程度）各自独立裁剪，LOD-0~3 即四维参数的四组预置组合，作用于统一生成结果之上。

- 备选：为每个 LOD 写独立生成逻辑。缺点：四份代码四份维护，且 LOD 之间难以保证一致性。
- 备选：只对序列化文本做裁剪。缺点：对象模型含超出 LOD 的字段会让下游误用，契约要求 LOD 控制"纳入候选集合的元素数量"与"每个节点携带字段"。
- 理由：先完整生成、按四维裁剪，各 LOD 可断言"符合维度定义"，token 预算超限检测也在裁剪后评估。

### D5：序列化器只面向 LLM 可读性，ref 由引擎确定性分配

区域/元素/文本承载元素按 §7.6.2 渲染规则输出；part-of=缩进、value-of=并列、related-to=括号标注（带分数）；兄弟按视觉顺序；id/bounds 不进文本，confidence 仅歧义时标注。ref 分配与解析由引擎持有的确定性 ref 映射表完成。

- 备选：让序列化文本同时兼容机器解析（如增加标记语法）。缺点：两头不讨好（契约 §7.2 明确反对）。
- 备选：ref 由 LLM 记忆跨快照（稳定 ref 方案 A）。缺点：页面动态变化时身份跟踪易错，违背确定性原则。
- 理由：方案 B（会话内即用即弃）已定案（§7.8）；序列化只服务 LLM 阅读，机器侧用对象模型。

### D6：每次调用完整生成，token 预算超限检测独立成层

`semantic_graph` 每次调用都执行程序化 + LLM 填充；预算检测基于 LOD、范围与序列化估算量，超限时报告（可失败或提示降级），不静默截断。

- 备选：结果缓存 + 失效机制。缺点：任何页面变化（含 input 值）都可能影响 LLM 判断，缓存有返回过期语义图的风险（§9.5 明确否决）。
- 理由：正确性优先于 token 成本，宁可多花 token。

## Risks / Trade-offs

- [每次生成都调 LLM，token 开销大] → 以 LOD/范围控制信息量（§9.5 四维参数），预算超限可检测、可降级。
- [related-to 打分质量依赖 LLM，测试不稳定] → LLM 填充 mock 化，程序化候选独立断言；集成冒烟（真实 LLM）单独标记为可选。
- [可见性判断存在陷阱（display:none/opacity:0/aria-hidden/视口外）] → 以 M1 DOM 快照的可见性字段为准，筛选规则按 §8.4 ⑤ 统一剔除；视口外元素在滚动类页面中按当前范围如实处理。
- [超大页面序列化文本仍可能超预算] → §7.6 蒸馏（只渲染有用字段）+ LOD 分级呈现，配合预算超限检测兜底。
- [DOM 快照依赖 M1 的爬取契约，契约变化会影响 M4] → M4 只消费 M1 快照数据契约（`docs/specs/M1-browser-driver.md` §5.4/§5.5），快照可 mock，耦合面收敛在该数据契约上。

## Migration Plan

M4 为新增模块，无既有实现需要迁移。接入顺序：先实现程序化阶段（可独立测试）→ 接入 LLM 填充（先 mock、后接 M0）→ 实现接口与序列化 → 集成到 M5 引擎函数层。回滚：M4 未上线前 M5 不依赖它，模块独立可回退，不影响其他模块。

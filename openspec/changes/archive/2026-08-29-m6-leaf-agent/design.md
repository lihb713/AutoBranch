## Context

动机见 proposal.md — Why。当前状态与约束：

- WebOps 采用"流程流转确定、LLM 只在叶子节点内行使有界执行权"的架构（契约 §5.7.2），叶子（Action/Condition）执行由 agent 式交互完成，组合节点为纯程序确定性遍历（M7）。
- M6 是执行层核心，依赖 M0（LLM 客户端，agent 多轮工具调用会话）与 M5（引擎函数层，含操作函数、semantic_graph 与 `OpResult` 错误语义）。M5 已定义 `OpResult(ok, error)` 与致命错误抛 `FatalBrowserError` 的语义（M5 spec §5.5）。
- 契约对引擎/LLM 边界有明确划分（§5.7.2.1）：引擎只负责告知任务、设置终止条件、记录错误日志，不干预 LLM；LLM 自主决定调用哪些函数、失败后自行修正。
- 叶子终止条件、定位终止条件、错误分类（LLM 侧 vs 程序侧）均已定义在契约（§5.7.2.1/§9.4/§9.6/§9.7），本模块将这些契约落为可测试的代码。
- 语义图每次调用都完整生成、无缓存（§9.5），LLM 可自由多次调用 semantic_graph 缩小/放大（§9.6）。

## Goals / Non-Goals

**Goals:**
- 提供 `execute_leaf` 统一入口，覆盖 Action 与 Condition 两种叶子，输出 `LeafResult`（状态 + 布尔值 + 错误来源 + 追踪数据）。
- 复用 M0 的 agent 会话能力，将 M5 引擎函数集作为工具注入，LLM 自主调用；引擎以循环驱动 agent 直至返回结果或触发终止。
- 实现三类引擎兜底终止条件（轮数上限 / 连续无进展 / 单叶子超时），触发即终止叶子并记为 LLM 侧失败。
- 实现错误边界：函数失败（`OpResult(ok=False)`）回传 LLM；程序侧致命错误直接终止整个流程并分类为程序侧失败。
- 提供可回归的提示词（固定输入 → 稳定 LLM 决策），并在 mock M5/M0 下完整可测。

**Non-Goals:**
- 不实现控制流遍历（M7 职责）——`execute_leaf` 只执行单个叶子，不做 Sequence/Selector/Repeat 流转。
- 不生成语义图（M4/M5 职责），只消费 M5 的 semantic_graph 工具。
- 不负责报告渲染与持久化（M8 职责），只产生 `LeafTrace` 追踪数据供读取。
- 不引入重试策略判断——引擎不判断该不该重试，只统计轮数与记录日志。
- 不实现定位专用逻辑——多轮定位就是"semantic_graph 作为普通工具被 LLM 自主多次调用"，定位终止是叶子终止的子集，统一由引擎终止条件覆盖。

## Decisions

### D1. 复用 M0 agent 会话，引擎只做循环驱动

M6 不自行实现工具调用协议，而是复用 M0 的 agent 会话（系统提示词 + 消息历史 + 工具 schema），引擎以一层循环驱动：调用 M0 获得下一步动作（工具调用或最终回答）→ 若是工具调用则经 M5 `EngineFunctions` 执行并回填 `OpResult` → 若为最终回答则解析为叶子结果。

- **理由**：函数调用协议、历史管理与 token 统计属于 M0 职责，避免重复实现；M5 已提供工具注册表（`ENGINE_TOOLS`）与执行实现，M6 只需把它们接进会话。
- **备选方案 A（M6 自实现工具调用循环）**：自行管理消息与工具执行。缺点：与 M0 职责重叠，M0 演进需同步修改。
- **备选方案 B（M5 直接执行）**：让 LLM 一次性输出完整计划再逐条执行。缺点：无 agent 语义，无法在失败后自主修正。

### D2. 终止条件由引擎在驱动循环内检测

引擎在每轮工具调用后检查三类终止条件：轮数上限（如 10 轮）、连续无进展（对连续多轮的调用/结果做指纹比较，检测结果未变或重复相同调用）、单叶子超时（墙钟计时，纳入全局 timeout）。任一触发 → 终止叶子、`status=failure`、`error_source="llm"`、`terminator` 记录触发条件。

- **理由**：契约 §5.7.2.1 明确引擎只设置与检测终止、不干预 LLM；把检测放在驱动循环内是唯一干预点，LLM 黑盒不受打扰。
- **备选方案 A（LLM 自查）**：让 LLM 自己判断是否无进展。缺点：LLM 可能为省 token 提前终止或卡死不退出，无法兜底。
- **备选方案 B（消息历史 token 预算）**：按累计 token 限制。作为补充项（定位的 token 预算已在契约 §9.7 提及），但主终止以轮数/无进展/超时为准，避免 token 计算歧义。

### D3. 多轮定位零专用逻辑，由 LLM 全权控制

semantic_graph 作为 M5 的普通工具暴露给 LLM，M6 不为定位写任何搜索策略代码——缩小、放大、回溯全部由 LLM 通过多次调用（不同 scope/LOD）自主完成；定位终止（§9.7 的轮数上限、连续 2 轮相同判断、token 预算）由 D2 的引擎终止条件统一覆盖。

- **理由**：契约 §9.6 明确"搜索控制权完全归 LLM"，且 §9.7 的定位终止条件是叶子终止条件的子集。零专用逻辑最贴近契约，也避免引擎对 LLM 搜索策略的隐性干预。
- **备选方案 A（引擎实现候选排序/回溯）**：引擎维护搜索状态。缺点：违反"引擎不干预"，且重复实现语义图消费逻辑。

### D4. 错误边界按 M5 错误语义分层处理

- 函数失败（`OpResult(ok=False)`）→ 作为工具调用结果回传 LLM（agent 语义），引擎只统计轮数。
- 程序侧致命错误（M5 抛出的 `FatalBrowserError`）→ 引擎捕获后立即终止整个流程，`status=failure`、`error_source="program"`。
- `LeafResult.error_source` 默认缺省；仅当程序侧致命错误触发时填 `"program"`，其余失败（含终止）一律 `"llm"`。

- **理由**：契约 §9.4 按错误源而非断言/异常分类，两类失败处理语义完全不同（LLM 侧重试无意义、程序侧重试有意义），必须在结果契约上显式区分。
- **备选方案 A（异常类型细分）**：以异常类区分错误。缺点：与契约"按错误源"的分类意图不一致，且难映射到报告分流。

### D5. 结果与追踪数据结构

`LeafResult` 含 `status`（success/failure）、`bool_value`（Condition 专有）、`error_source`（失败时 llm/program）、`trace`（`LeafTrace`：`llm_input`、`llm_reasoning`、`calls`（`ToolCallRecord` 序列）、`terminator`）。追踪数据在驱动循环内逐步累积，最终随结果返回，供 M8 回溯。

- **理由**：契约与 M6 spec §5.1/§5.2 直接定义了这些结构；逐轮累积保证报告能还原完整执行过程。
- **备选方案 A（仅返回状态）**：丢弃中间过程。缺点：M8 无法回溯，违反验收标准"执行追踪数据完整"。

### D6. 提示词为版本化固定模板

叶子执行提示词采用固定模板：系统提示词（角色与行为准则）+ 节点描述 + 语义图正文，模板版本号随变更递增；相同输入下决策可被记录并用于回归比较。

- **理由**：契约 §10.1-5 要求提示词可靠驱动决策；版本化使提示词回归测试成为可能（固定输入 → 记录 LLM 决策 → 变更后对比）。
- **备选方案 A（动态拼装、无版本）**：维护简单但无法回溯决策漂移，回归测试无从谈起。

### D7. 测试以 mock M5/M0 为主，不依赖 M7

M6 测试全部以 mock 驱动：mock M0 为固定响应 LLM 桩（预置工具调用序列或最终判断），mock M5 的 `EngineFunctions` 返回固定 `OpResult`。测试覆盖 agent 决策序列、三类终止条件、Condition 布尔结果、错误分流与提示词回归。

- **理由**：M6 spec 测试策略要求独立性（不依赖 M7）；真实浏览器/语义图留待 M7 集成验收。
- **备选方案 A（真实浏览器集成）**：更接近真实但脆弱、慢，且与 M6 职责边界（只测决策与兜底逻辑）不符。

## Risks / Trade-offs

- [LLM 不遵循工具 schema 或产生幻觉调用] → 引擎把非法调用以失败工具结果回传 LLM 让其修正；同时以轮数上限兜底，避免死循环。
- [终止条件误判"无进展"，把正常的慢搜索提前终止] → 无进展检测采用"连续多轮完全相同的调用/结果指纹"的保守判定（契约 §9.7 亦为连续 2 轮），并允许配置轮数阈值。
- [语义图每次完整生成导致 token 消耗高] → 这是契约既定取舍（§9.5 正确性优先），M6 不缓存；token 预算作为定位终止的补充条件在 D2 中预留。
- [提示词变更导致 LLM 决策漂移] → 提示词版本化 + 回归测试（D6），变更必须通过回归对比才能合入。
- [LLM 侧失败与程序侧失败的边界模糊（如元素不存在的归因）] → 以"是否确定性程序错误"为准：仅致命错误（浏览器崩溃/网络断开）归程序侧，其余一律 LLM 侧，避免二义。
- [M0 会话的 agent 能力（如是否支持并行工具调用）差异影响 M6 假设] → 在 M6 与 M0 的接口测试中固定会话调用方式，适配差异集中在 M0 适配层。

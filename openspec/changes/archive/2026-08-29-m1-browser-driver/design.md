## Context

WebOps 的引擎需要在真实浏览器中执行页面操作、HTTP 请求与 DOM 数据采集，但目前代码库尚无任何浏览器相关代码。本设计对应的动机与范围见 `proposal.md`（Why / What Changes），行为契约见 `specs/browser-driver/spec.md`。当前约束来自契约文档：

- 每次 run 必须全新会话、无持久化、全流程共享一个 context（§5.9），跨运行复用登录态不在支持范围。
- 页面是一类变量（页面引用），操作必须作用于"当前页面变量指向的页"，多页并存时互不干扰（§5.10）。
- HTTP 接口分形态：形态A 读取页面已发生请求的响应，形态B 发起不经页面的独立请求且认证信息显式提供（§5.8.2）。
- 错误按源分类：程序侧失败（元素不存在/网络超时）返回可分类失败结果，致命错误（浏览器崩溃/网络断开）抛出 `FatalBrowserError` 终止流程（§9.4）。
- DOM 爬取需输出节点树/role/可见性/包围盒/程序化值，供 M4 语义图程序化阶段使用（§8.3），且只覆盖主文档、不处理 iframe 与动态渲染（§8.9）。

## Goals / Non-Goals

**Goals:**
- 以 Playwright 为底层封装，对外提供稳定、可独立测试的浏览器驱动接口。
- context 生命周期与契约完全一致：冷启动、无持久化、stop 完整释放。
- 操作函数全部显式绑定页面引用，多页并存时行为确定。
- HTTP 两种形态行为可预测、可测试；形态B 绝不自动附加页面会话 cookie。
- DOM 爬取输出可编程使用的快照，与 M4 的筛选规则（§8.4）对齐。
- 模块无依赖，可在独立 conda 环境内用真实浏览器跑通全部测试。

**Non-Goals:**
- 不做 iframe 内元素的爬取与操作路由（§8.9 明确第一版范围外）。
- 不做懒加载/虚拟滚动/动态渲染处理。
- 不做跨运行 cookie/登录态持久化。
- 不做元素身份稳定跟踪（ref 即用即弃，§7.8 策略B）；本模块只负责"引用→DOM 节点→执行"的确定性解析。
- 不实现语义图（purpose/related-to 填充属 M4 + LLM 职责）。

## Decisions

### D1 底层封装选型：Playwright
- **选择**：Playwright（Python）。
- **理由**：原生支持多标签页/context 隔离、自动等待与 actionability 检查、response 事件监听、download/upload 与多浏览器；context 可精确控制 cookie 隔离，契合冷启动要求。
- **备选**：Selenium（需自行管理 driver 与等待策略，事件监听弱）、pyppeteer/CDP 直连（需手写协议层，成本高）。Playwright 的封装深度与契约需求的匹配度最高。

### D2 context 会话：每次 start 全新、无持久化
- **选择**：每次 `start` 创建全新 context；`stop` 关闭 context 及全部页面。
- **理由**：契约 §5.9 强约束，可复现性优先；冷启动保证第二次执行登录流程仍然生效。
- **备选**：持久化 cookie/复用登录态——被契约明确排除（破坏可复现性），不采纳。

### D3 页面引用标识：会话内自增 id，即用即弃
- **选择**：`PageRef` 使用会话内自增 id，仅在本会话内有效；stop 后全部失效。
- **理由**：与 §7.8 ref 桥策略B（即用即弃、无身份跟踪）一致，确定性高；无需跨快照追踪元素身份。
- **备选**：稳定 ref（DOM 特征/路径跟踪元素身份）——页面动态变化时身份跟踪易错，且契约倾向 B，不采纳。

### D4 操作绑定方式：操作显式接收 page_ref
- **选择**：所有页面操作函数把 `page_ref` 作为显式参数（驱动层为 `PageHandle` 视图，按引用解析到真实页面）。
- **理由**：避免"全局当前页面"共享可变状态；与 §5.10 页面变量机制一致——变量指明操作哪一页，驱动层只做确定性解析。
- **备选**：维护全局"当前页面"指针由引擎切换——引入隐式共享状态，多页并发/嵌套执行时易错，不采纳。

### D5 HTTP 监听（形态A）：response 事件 + 内存记录表
- **选择**：订阅 Playwright 的 response 事件，把请求（method、URL、状态、响应体等）追加进会话级内存列表；`clear` 截断列表；`get_response(method, url_pattern)` 按 method 精确匹配 + URL 模式匹配（实现期采用子串/通配匹配，可后续收紧）返回首个匹配项。
- **理由**：形态A 语义即"读取页面已发生的请求"（§5.8.2），事件监听成本低、无侵入。
- **备选**：请求拦截注入（route 代理）——可读响应但不改动请求路径时属于过度设计，且影响页面加载行为，不采纳。

### D6 独立请求（形态B）：独立 HTTP 客户端，不经浏览器 context
- **选择**：`http_request` 使用独立 HTTP 客户端（首选 `requests`，备选标准库 `urllib`）发起，不经过浏览器 context.request。
- **理由**：§5.8.2 形态B 要求"认证信息由用户显式提供、不从页面会话自动提取、不维护 cookie"；独立客户端天然满足，避免 context.request 附带会话 cookie 的隐患。
- **备选**：Playwright 的 APIRequestContext——其 cookie 行为易与页面会话耦合，需额外隔离代码，不采纳。

### D7 DOM 爬取：页面内注入 JS 遍历主文档
- **选择**：`DomProbe.crawl(page_ref, LOD)` 在页面内执行一段注入脚本，遍历主文档：构建节点树、读取 role/aria 语义、计算可见性与包围盒 bounds、读取程序化值（value/checked/disabled/文本），按 §8.4 规则过滤隐藏、零尺寸、aria-hidden 元素，按 LOD 控制信息量。
- **理由**：脚本在浏览器环境内直接访问布局与运行时状态，能拿到可见性/包围盒/程序化值这些无法从服务端 DOM 获得的数据；一次注入返回完整快照，性能可控。
- **备选**：服务端解析原始 HTML（只能拿到结构，无法获得几何与运行时状态）、a11y 树导出（丢内容、无布局）。两者都无法满足 §8.1 三信息源中"几何/程序化值"的要求，不采纳。

### D8 错误语义：操作异常分类 + 致命错误上抛
- **选择**：操作函数内部捕获可预期的程序侧异常并分类（元素不存在/超时/等待超时等），返回 `ok=False` + 错误码 + 错误信息；浏览器崩溃、网络断开、context 关闭等致命异常不捕获，直接抛出 `FatalBrowserError` 终止流程。
- **理由**：§9.4 按错误源分类——程序侧失败可重试、致命错误重试无意义，两种处理方式不同，必须在驱动层就分界。
- **备选**：统一把异常转为失败结果返回上层再分类——致命错误被吞掉会导致流程继续对死掉的浏览器操作，语义错误，不采纳。

### D9 数据契约：OpResult / ElementRef / PageRef
- **选择**：`OpResult(ok, error, detail)` 作为所有操作的统一返回；`ElementRef(id)` 为引擎侧元素引用（来自 ref 映射表）；`PageRef` 为页面引用。
- **理由**：统一结果结构便于 LLM 作为工具结果回读（§5.8.1），detail 预留扩展位。
- **备选**：每类操作各自返回结构——增加调用方分支成本，不采纳。

### D10 测试策略：真实浏览器 + 本地测试网页 fixture
- **选择**：独立 conda 环境内安装 Playwright 与浏览器；用本地静态服务器/测试网页 fixture 覆盖各操作函数、多页/多标签、HTTP 监听、download/upload、截图与 DOM 爬取；模块测试不依赖 LLM 与行为树。
- **理由**：M1 spec 明确"真实浏览器测试"且要求模块独立性；本地 fixture 可控、可离线、无外网依赖。
- **备选**：mock 浏览器层——无法验证真实浏览器行为，达不到验收标准，不采纳。

## Risks / Trade-offs

- [Playwright 浏览器二进制安装体积大、首次下载慢] → 在 conda 环境内一次性安装并锁定 Playwright 版本；测试服务器用本地 fixture 避免外网。
- [浏览器执行环境的平台差异（Windows）] → 统一使用 Playwright 管理的浏览器二进制，不依赖系统浏览器。
- [每次会话冷启动、无持久化导致重复执行登录流程成本高] → 契约明确接受此代价以换取可复现性（§5.9），不属于本模块可裁量范围。
- [每次 DOM 爬取实时读取程序化值，大页面可能较慢] → 由调用方按 LOD 控制信息量（§9.5），本模块只保证快照正确性。
- [get_response 的 URL 模式匹配规则过于简单可能误匹配] → 第一版采用子串/通配匹配，匹配语义在实现期明确并测试固化；后续可按需收紧。
- [Playwright API 随版本演进变化] → 锁定版本并保留薄封装层，隔离 API 变动对上层的影响。
- [request 记录的内存增长] → clear 提供显式清理语义，记录列表生命周期随会话；超大流量场景由调用方控制清理节奏。

## Migration Plan

本 change 是全新模块，无既有实现需迁移。落地即完成模块独立交付，不改变其他模块行为；M4/M5/M8 后续按依赖引入。回滚策略：模块独立、无全局状态改动，移除或替换不影响其余代码。

## Open Questions

- 错误码枚举的具体粒度（如超时细分为页面加载/等待/网络）可在实现期细化，不影响 spec 的"可分类错误码"契约与任务划分。
- `get_response` 的 URL 模式匹配语法（子串/通配）的最终细节可在实现期结合测试用例定死，不影响 spec 契约。

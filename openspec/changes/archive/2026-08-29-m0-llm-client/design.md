## Context

M0 LLM 客户端是 WebOps 全部 LLM 交互的唯一入口，被 M6（叶子 agent 执行）与 M4（语义图生成 LLM 填充阶段）复用。当前代码库尚无任何 LLM 相关实现，本 change 从零落地该模块。约束来自 `docs/specs/M0-llm-client.md`：**无依赖、最早实现、可独立测试**；契约 `docs/contract.md` §6 要求支持任意 OpenAI 兼容端点（base_url + api_key + model），§5.7.2 要求 agent 式多轮工具调用会话，§9.4 要求按错误源分流（可分类异常）。动机见 proposal.md 的 Why，行为契约见 specs/llm-client/spec.md。

## Goals / Non-Goals

**Goals:**
- 提供一个传输层可替换的 LLM 调用封装：默认走真实 HTTP，测试时注入 fake 传输，实现"Mock HTTP"独立测试策略
- 以内部统一消息模型承载 Chat Completions 与 Responses 两种协议形态，协议差异收敛在适配层
- 会话内消息序列累积 + token 统计 + 预算超限检测，全部在客户端内完成，不依赖上层
- 错误按类别抛出，调用方（M6/M4）无需解析 HTTP 细节即可分流处理

**Non-Goals:**
- 不接入 Anthropic / Gemini 等非 OpenAI 兼容厂商（契约 §6.1 第一版范围外）
- 不做模型自发现 / 模型路由
- 不做重试策略本身（错误分类后由调用方决定是否重试，契约 §9.4）
- 不实现工具的实际执行（执行归 M5/M6，M0 只负责调用与回填）

## Decisions

### D1: 直接调用 OpenAI 兼容 HTTP 接口，不引入 openai SDK

使用传输适配层直接构造 / 解析 OpenAI 兼容协议的 HTTP 报文，不依赖官方 `openai` SDK。
- **理由**：SDK 绑定特定协议实现细节，对 vLLM / DeepSeek / Kimi / OpenRouter 等兼容端点的差异控制力弱；直接构造便于逐字段校验请求体，也便于用 fake 传输做确定性测试。
- **备选**：`openai` SDK —— 上手快，但抽象层掩盖协议细节，且 SDK 版本升级可能影响兼容端点，不符合"透明支持任意 base_url"的目标。

### D2: 传输层抽象（Transport），默认实现用标准库 urllib，测试注入 FakeTransport

定义薄传输接口（发起请求 → 返回状态码 + 响应体），默认实现基于标准库 `urllib.request`（零第三方运行时依赖，符合"无依赖"约束）；测试注入 FakeTransport 返回预设响应，从协议层验证请求体格式、工具回填与异常分类。
- **理由**：`docs/specs/M0-llm-client.md` §7 测试策略要求 Mock HTTP 拦截验证请求体；传输抽象把"网络"与"协议"解耦，使全部协议/会话/预算逻辑可离线测试，独立于浏览器与行为树。
- **备选**：`requests` / `httpx` —— API 更友好，但引入第三方依赖；`responses` 库 mock —— 绑定 `requests` 生态，且只能 mock 默认实现而非任意传输。

### D3: 双协议形态统一为内部消息模型，差异收敛在协议适配层

Chat Completions 与 Responses 各有独立的请求构造与响应解析实现，二者都映射到同一内部消息序列与同一 `LLMResponse` 结果结构（text / tool_calls）。
- **理由**：两种形态报文结构不同（messages/tools vs input/instructions），统一内部模型后，会话层（消息累积、工具回填、预算）只面对一种模型，协议切换只影响适配层；至少实现一种可测形态，另一种随测试补齐（M0 spec §6 验收）。
- **备选**：只做 Chat Completions —— 实现更少，但与契约 §6.1"支持 Chat Completions 与 Responses 两种协议形态"不符。

### D4: LLMSession 持有完整消息序列，每次 request 全量携带

会话内部维护 system 提示词 + 用户/助手/工具消息的有序列表；`add_user_message` / `add_tool_result` 追加消息，`request` 将全量序列交给适配层构造请求报文。
- **理由**：契约 §5.7.2 要求"上下文正确累积、工具结果不丢失"，全量携带保证模型看到的上下文始终完整，且实现简单、无增量同步的状态机复杂度。
- **备选**：增量发送 + 服务端上下文拼接 —— 依赖端点上下文管理能力，兼容性差，放弃。

### D5: token 统计优先取响应 usage，缺失时保守估算

`request` 后读取响应的 token 用量字段（prompt + completion 或 total）累加进会话；端点未返回用量时，退化为按消息内容长度做保守估算，并在统计结果中标注估算来源。
- **理由**：预算检测需要相对准确的累计值；多数 OpenAI 兼容端点返回 usage，精确累加可行，缺失时保守估算避免"预算形同虚设"。
- **备选**：只依赖 usage 字段 —— 端点不返回时无法检测预算，不可接受。

### D6: 错误分类按来源映射，预算超限本地检测

网络/连接异常 → `LLMConnectionError`；HTTP 401/403 → `LLMAuthError`；请求超时 → `LLMTimeoutError`；本地累计 token 超过预算 → `LLMBudgetExceeded`（与端点响应无关）。
- **理由**：契约 §9.4 按错误源分流——程序侧（连接/超时）重试有意义，LLM 侧/配置问题（鉴权）重试无意义；预算超限由 M6 终止叶子，须在客户端内尽早抛出。
- **备选**：统一抛一个 LLMError 让上层再解析 —— 违反"可分类异常由调用方按错误源分流"的契约要求。

### D7: 流式/非流式双通道，第一版以非流式为主

非流式作为默认与验收路径；流式作为可选能力，通过请求参数开启，响应按 SSE 分段解析后汇聚。
- **理由**：批处理模式（契约 §6.2）非流式已满足需求且实现简单；保留流式能力为后续长上下文/进度场景预留，但不阻塞第一版。
- **备选**：第一版只做非流式 —— 更少代码，但"可选流式"能力（M0 spec §2）无法验证。

## Risks / Trade-offs

- [token 估算可能不准] → 优先使用端点 usage 字段精确累加；仅缺失时估算并标注，预算上限设置留出余量。
- [兼容端点的协议细节差异（如 tools 字段格式、响应结构不一致）] → 协议适配层集中收敛差异；真实 API 冒烟测试作为可选验收项，Mock 测试保证核心行为。
- [不引入 SDK，报文自行构造易出错] → 传输层 + 适配层拆分，请求体构造逐字段有测试覆盖；结构化数据类（ToolSpec/ToolCall）约束字段。
- [流式解析复杂度] → 流式标记为可选能力，非流式路径不受影响；流式汇聚结果与非流式一致性用测试校验。
- [api_key 泄露风险] → 配置字段不进入日志/报告，测试用假密钥断言日志无明文。

## Migration Plan

本模块为新增模块，无既有代码迁移。落地顺序：传输层 + 配置结构 → 单协议（Chat Completions）请求 → 会话与工具回填 → 预算与错误分类 → Responses 适配 → 流式可选能力。对 M6/M4 的接入属于下游 change，本 change 只交付 M0 客户端本身及其测试。

## Open Questions

- 预算上限的具体数值与配置来源（默认值、由 M6 传入还是全局配置注入）——由上层调用方决定，不影响 M0 客户端"检测并抛出"的能力，可延后。
- token 估算的保守系数——属于实现细节，可延后调整，不改变 spec。

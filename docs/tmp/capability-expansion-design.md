## 1. 背景与目标

当前 Action/Condition 实质只支持**网页操作**（LLM agent + 浏览器工具集）。
目标：把 AutoBranch 扩展为**通用的、基于 LLM 的行为树自动化工具**，网页自动化退化为
**其中一项能力**。

期望能力举例：数值运算、页面判断并写布尔值、排序、文件对比、远程虚拟机执行命令等。
不追求一次支持全部，重点是**能力边界与架构可扩展**。

## 2. 核心统一模型：函数注册表

两种使用方式并存，但落在**同一个函数注册表**上：

```
                函数注册表 (FunctionRegistry)
                ┌──────────────────────────────────┐
                │ multiply(a,b) → 值                 │
                │ sort(数据) → 结果                  │
                │ ssh_exec(session, cmd) → 输出       │
                │ open/click/extract…（浏览器函数）    │
                └──────────────────────────────────┘
                      ▲                    ▲
        分叉B（确定性） │                    │ 分叉A（LLM）
      ┌───────────────┴──────┐   ┌─────────┴──────────────────┐
      │ FunctionCall 节点      │   │ Action（LLM agent）         │
      │ 直接调函数，不经 LLM    │   │ 描述 + 能力工具集 → 决策     │
      └──────────────────────┘   └────────────────────────────┘
```

- **分叉 A（需要）**：即使操作确定（如乘 2），"用自然语言描述获取结果"仍需要 LLM
  理解含义并调用对应方法。故 Action（描述 + LLM + 工具）保留。
- **分叉 B（需要）**：一系列确定操作用自然语言描述反而复杂化——直接实现为 Python
  函数，用 **FunctionCall 节点**调用，确定性、可预测。

## 3. FunctionCall 节点（≈ ref 的"函数版"）

```
ref 节点:            FunctionCall 节点:
  target: 文档名        function: 函数名
  args: [值...]         args: [值...]        ← 实参入口（本树变量名或字面量）
  returns: {名: 类型}    returns: {名: 类型}  ← 返回值出口（回收进当前帧）
```

- 执行：求值 args → 校验函数签名 → 调 Python 函数 → 返回值按 returns 回收。
- **确定性**、不经 LLM；与 ref 执行同构（ref 加载文档执行，FunctionCall 调函数）。
- **多返回值**：函数返回**命名结果**（如 `{"stdout": "...", "code": 0}`），
  `returns` 按名回收；单值也兼容。
- **异常语义**：函数抛异常 = 该节点 FAILURE（程序侧，含函数名/错误），与 ref 加载
  失败一致，不影响其他节点。

## 4. 插件模型

### 4.1 一个插件 = 一个 Python 包

```
plugins/                        ← 插件根目录（引擎扫描）
├── ssh/
│   ├── __init__.py             ← 入口：import 触发注册
│   ├── functions.py            ← 层级1：@engine_function 对外函数
│   └── pool.py                 ← 层级2：底层封装（如 SshSessionPool）
├── strings/
│   ├── __init__.py
│   ├── functions.py
│   └── utils.py
└── _common/                    ← （可选）跨插件共享的底层包
    └── net.py
```

### 4.2 显式注册（非全模块注册）

只有被显式标注的函数进入注册表；工具函数/类**不注册**：

```python
@engine_function("ssh_exec", returns={"stdout": "str"})
def ssh_exec(session, command: str) -> dict:
    return {"stdout": _run(session, command)}

def _run(session, command):   # 辅助函数：不注册
    ...
```

### 4.3 两个层级与代码组织

- **层级 1（对外引擎函数）**：`@engine_function` 标注，暴露给 LLM 工具 / FunctionCall。
- **层级 2（底层公共类/方法）**：供层级 1 复用，可放插件包内，或被多个插件共享
  （`_common/` 共享包）。

**扩展方式**：新增一个能力域 = 新增一个插件包（层级1 + 层级2），互不干扰。

### 4.4 插件入口约定

- 引擎**扫描 `plugins/` 下每个子包并 import 其 `__init__.py`**；`__init__.py` 里
  `from .functions import *` 触发注册。
- 需要元数据时再加可选 `plugin.toml`（非必需）。

### 4.5 不区分"内置 / 用户"

所有函数都是插件：引擎自带的函数也以插件形式随引擎分发；用户新增的插件放同一
扫描根，**全部加载**。机制完全一致（同一 `@engine_function` + 同一注册表 + 同一
调用路径）。"内置 vs 插件"是伪二分，已取消。

### 4.6 引擎核心 vs 插件：判断标准与变量读写归属
**判断标准**：

```
操作「行为树自身状态」（变量空间 / 执行帧）  →  引擎核心
操作「外部能力」（浏览器 / SSH / 文件 / 计算…）  →  插件（对 LLM 暴露）
```

**引擎核心**（行为树设计 + 机制）：解析、遍历编排、流程控制节点（Sequence/Selector/
Repeat/IfThenElse/Branch）、ref、FunctionCall、报告、LLM 客户端、**变量空间
（space/frame）与变量读写（get/set）**。

**插件**（外部能力，对 LLM 暴露）：浏览器、计算、SSH、文件等。

**变量读写归引擎核心，不对 LLM 暴露**——它操作的是变量空间，属于行为树设计的一部分，
不是扩展能力。

**推论：插件函数只「返回值」，变量写入由引擎落笔**：

```
现状（错位，待改）:
  LLM 调 extract(ref, target) → M5 内部 space.write(target, value)   ← 插件写变量

新设计:
  LLM 调 extract(ref) → 插件返回 value（只返回值）
  → 引擎执行器按节点声明把 value 写进目标变量（引擎落笔）
```

- 读（get）：引擎侧（叶子执行前程序替换），LLM 不参与。
- 写（set）：LLM 选择"用哪个插件函数产出值" → 引擎把返回值写入声明变量。
- 两者都在**引擎侧落笔**；插件只提供"值"，不接触 space/frame。

### 4.7 模块组织：引擎核心 / 插件框架 / 具体插件

```
┌───────────────────────────────────────────────────────────┐
│ 引擎核心（行为树设计 + 机制）                                │
│  解析 · 遍历 · 流程控制 · ref · FunctionCall · 报告 · LLM    │
│  变量读写（space/frame）                                     │
├───────────────────────────────────────────────────────────┤
│ 插件框架（Plugin System）                                    │
│  插件注册表 · 加载/懒装配 · 能力选择(use_capability) · 分发   │
├───────────────────────────────────────────────────────────┤
│ 具体插件（Plugins）                                          │
│  浏览器 · 计算 · SSH · 文件 …（各自 FunctionDef）            │
└───────────────────────────────────────────────────────────┘
```

- **`use_capability`** 属于**插件框架**（框架级工具），**不属于任何具体插件**——
  它负责"加载/初始化某个能力"（即调用该插件的 `init`）。
- 工具集 = 框架工具（`use_capability`）+ 已加载插件的函数。
- 选能力 = 调用框架工具 `use_capability(name)`（**复用现有 tool_calls 机制**，
  无需新的 LLM 输出协议；`parse_final_decision` 与循环分流不变）。

### 4.8 插件来源与目录组织（双路径）

**双路径**：

```
① 预置插件（文件系统）
   plugins/ 下的**包**；启动扫描 + import；可 import common + 三方库；开发者维护。

② 用户自定义插件（数据库）
   源码存 DB；加载用 compile + exec（注入 @engine_function 注册器）；
   **仅标准库**，不 import 其他插件 / common / 三方库。
```

```
plugins/
├── browser/          ← 预置插件（包，可用 common + 三方库）
│   ├── __init__.py
│   └── functions.py
├── ssh/              ← 预置插件（包）
├── compute/          ← 预置插件（包）
└── common/           ← 共享库（非插件；不注册函数、不对 LLM 暴露）
```

- **无 `custom/` 目录**：自定义插件源码存 **DB**（Web 编辑天然、重载简单）。
- **`common`**：共享库，不是插件——不注册函数、不对 LLM 暴露；只被预置插件 `import`。
- **加载器两条路径**：预置插件扫描 `plugins/` 子包（排除 `common`）→ `import`；
  自定义插件从 DB 读源码 → `compile` + `exec`。两者同一注册路径（`@engine_function` +
  同一注册表）。

## 5. 运行时资源与依赖注入

### 5.1 结论：取消「函数级资源注入（requires）」

- **组件级依赖注入（保留）**：引擎自身的装配（见 §6），解决可测试/可替换/共享
  状态/生命周期。
- **函数级资源注入（取消）**：session 等运行时对象**作为黑板变量（值）传递**，
  与 `page_ref` 同构，不注入。

```
页面变量（现有）:              SSH session（新）:
  open(url) → page_ref           create_session(ip,user,pwd) → session
  存黑板变量                     存黑板变量
  后续操作作用于该页面            后续 ssh_exec(session, cmd) 显式传入
```

session 是**值**不是引擎资源；函数是**纯参数化**的（输入 → 输出），无隐藏状态。

### 5.2 session 的建模

- **类型**：类型系统支持一个**泛型"引用/对象"类型**（或 `session` token）。
  **展示由 Python 类型的 `__str__` 定义**，引擎不做特殊渲染（呈现是类型内部的事）。
- **生命周期**：提供 `close_session(session)` 函数，由 LLM 按描述**显式调用关闭**；
  引擎不自动回收。
- **函数只通过返回值影响行为树**（returns 回收），不直接写黑板（保持纯函数）。

## 6. 依赖注入的重新审视（能力为中心）

当前 `browser` 注入是"浏览器为中心"的假设。新设计下：

```
Engine 核心注入（总是需要）:
  space_factory（变量）、config、current_frame 提供者

能力依赖（按能力装配，可选）:
  浏览器能力  → browser, filler, graph_generator, probe
  计算能力    → （无）
  SSH 能力    → （无，session 走值传递）
```

- `browser` 不再注入给"引擎"，而是**注入给"浏览器能力插件"**——只有真正用到
  浏览器操作时才需要它。
- **浏览器操作也是插件**（open/click/extract… 是一组插件函数），既可由 Action
  的 LLM 调用，也可由 FunctionCall 调用，与其他插件一致。

## 7. 能力按需装配（懒装配）

### 7.1 两级选择（LLM 确定能力）

```
① 先给 LLM「能力清单」（概览：浏览器/计算/SSH，各一句说明）
   + 框架工具 `use_capability(name)`（name 的 enum = 所有能力名）
② LLM 调用 `use_capability("ssh")`（= 选能力）
③ 引擎调 ssh 插件 `init`（初始化公共资源）→ 把该能力的函数集追加进工具集
④ LLM 选具体函数（ssh_exec）调用
```

- **选能力 = 调用框架工具 `use_capability(name)`**（复用现有 `tool_calls` 机制，
  无需新输出协议）。
- 一个 Action 内可**多次选能力**（多轮/多能力），工具集随加载增长。

理由：用户写行为树时只写自然语言，不知道引擎有哪些能力；由 LLM 依据**良好的提示词**
先选能力、再选函数，避免全量工具清单膨胀（两轮候选更少，选择更准）。

### 7.2 懒装配发生在「调用分发」时

```
Engine 启动：只装配核心（space + FunctionRegistry + LLM config）
叶子执行：LLM 选函数 → 引擎分发时发现插件未加载 → 懒加载插件 → 装配其依赖 → 执行
```

- 纯计算/SSH 行为树：零浏览器开销。
- 浏览器行为树：第一次用到浏览器函数时才装配 browser、启动浏览器。

### 7.3 浏览器生命周期

- **与现有一致**：行为树执行（run）结束后统一释放。
- run 内第一次用到浏览器函数才启动；run 结束释放。

## 8. 待定问题清单（依次讨论）

按讨论顺序编号，每项结论确认后回填本节。

- [x] **T1. 现有浏览器实现插件化改造**（讨论中，已定部分）
  结论：
  - 插件 = **插件类**（`name` / `description` / `function_defs()` / `init(runtime)` /
    `call(name, args)`）+ **结构化 `FunctionDef`**（名字/说明/参数/多返回值/实现）。
  - **浏览器插件自包含**：`browser` / `ref_map` / `semantic_graph` 都在插件内部，
    函数**只返回值**。
  - **变量读写归引擎核心**（§4.6）：插件不接触 `space`/`frame`；写变量由引擎落笔。
  - **懒装配**在 `call` 分发时触发：插件未初始化 → `plugin.init(runtime)`（插件自己
    初始化 browser / session 池等公共资源）→ 注册其函数 → 分发。
  - **两级能力查找**：`description` 供一级（选能力），`function_defs()` 供二级（选函数）。
  遗留：浏览器函数从 M5 拆出的具体形态（见 T10）。

- [x] **T2. 叶子执行的两级能力选择**
  结论：
  - **去掉叶子执行前的强制语义图预取**（浏览器专属）：改为 prompt 强调"操作/判断前
    先调用 `semantic_graph` 获取最新语义图"，由 LLM 自主决定调用时机（纯计算叶子
    零浏览器开销）。
  - **两轮选择**：① 给「能力概览」+ 框架工具 `use_capability` → LLM 选能力 →
    框架加载（调插件 `init`）→ ② 该能力函数追加进工具集 → LLM 细选函数。
  - **选能力 = 调用框架工具 `use_capability(name)`**，复用现有 `tool_calls` 机制，
    无需新的 LLM 输出协议（`parse_final_decision` 与循环分流不变）。
  - 支持一个 Action **多轮/多能力**（能力可中途追加；与现有多轮 agent 一致）。
- [x] **T3. 泛型对象类型**
  结论：
  - 类型系统统一为**泛型对象类型**（token 暂定 `object`）：不校验，`str(value)` 呈现，
    `_jsonable` 序列化。
  - **`page_ref` 纳入泛型**：它是**浏览器插件的对象类型**，非系统内置；引擎核心不再有
    `page_ref` / `current_page` / 页面变量概念（全部归浏览器插件）。
  - **三种类型层次**：① 变量声明类型（用户写 `object`，泛型不校验）② 函数签名类型
    （插件声明，约束在调用层）③ 实际值类型（函数返回值决定）。
  - **增强**：`FunctionDef` 声明返回类型；引擎写变量时记录"实际类型"（黑板/报告显示
    实际类型，校验放行）。用户只写 `object`，LLM 不需关心类型。
  待定：token 命名（`object` / `opaque` / `reference`）。
- [x] **T4. 插件加载时机**
  结论：
  - **启动时扫描唯一的 `plugins/` 目录，加载全部插件**（不区分引擎自带/用户）。
  - **插件开发对「开发者」开放，不对「终端用户」开放**：写插件的是工具开发者，
    不是行为树书写/运行的终端用户；**不存在**"终端用户 Web 上传插件"的场景。
  - 加载器写成可重入的扫描/注册（预留将来重载口），当前只做启动扫描。
- [x] **T5. 安全边界**
  结论：**不做安全机制**（无危险标记、无运行时确认、无权限/白名单）。插件由**内部
  开发人员**开发，信任其提供的能力；暂不需要额外保护。
- [x] **T6. 前端呈现**
  结论：
  - **FunctionCall 节点**：画布显示函数名（类似 ref 节点）。
  - **属性面板**：选插件/函数（下拉，按插件分组）→ 加载函数签名（参数 + 多返回值）
    → 填 args/returns；与 ref 节点编辑**对称**（选文档 → 加载 inputs/outputs → 填 args/returns）。
  - **后端 API**：提供「插件/函数清单」（注册表 → API），供前端下拉与签名加载。
  - 编辑期用户**显式选函数**；与运行期 LLM 的两级能力选择相互独立。
- [x] **T7. 两级能力选择的提示词与输出协议**
  结论：
  - **无需新的 LLM 输出协议**：选能力 = 调用框架工具 `use_capability(name)`，
    复用 `tool_calls`；`parse_final_decision` 与循环分流不变（仍是"工具调用 / 最终结果"两类）。
  - **能力概览**：由插件注册表生成（各插件 `description`），注入系统/用户提示词。
  - **函数清单**：插件加载后由其 `function_defs()` 生成工具 schema，追加进工具集。
- [x] **T8. 懒装配分发层设计**
  结论：
  - **注册表两层**：`known`（已知插件 + description，供能力概览 / `use_capability`
    的 enum）、`loaded`（已加载插件实例）、`functions`（已加载函数 → 插件 + FunctionDef）。
  - **分发**：查归属 → 懒加载 → 调用 → 产出型落笔。
  - **未加载函数被直接调**：**报错**（agent 语义，把错误信息返回给 LLM，提示"需先加载
    该插件"），**不中断程序**。
  - **产出型工具标注**：`FunctionDef` 元数据 `output_param`（声明哪个参数是变量目标）。
  - **插件生命周期与初始化由引擎控制**：LLM 表达意图（`use_capability` 请求加载 /
    函数调用请求）→ **引擎执行**（初始化插件 / 调用函数）。统一为"**LLM 决策，引擎执行**"。

- [x] **T9. 插件返回值 → 变量写入的映射机制**（方案 1）
  结论：
  - **工具 schema 带「输出目标」参数**（如 `extract(ref, target)`），LLM 填 `target`。
  - **插件函数只返回值**（`extract(ref) -> value`），不含 `target`。
  - **执行器识别"产出型"工具**：拆出 `target` → 调插件（剩余参数）→ 把返回值写
    `target`（**引擎落笔**）。
  - `target` 是"业务工具的输出目标"（不是"变量读写工具"），落笔在引擎，不违反
    "变量读写归引擎"。
  - `target` 须在节点 `[[set]]` 声明集内（保留现有校验）。
  待定细节：产出型工具的标注方式（参数名约定 `target`/`save_to` vs ToolSpec 元数据）。

- [x] **T10. M5 引擎函数层的重构**
  结论：
  - **M5 演化为「插件框架（Plugin System）」**：插件注册表 / 懒装配 /
    `use_capability` / 分发。
  - **浏览器拆成独立插件**（与计算 / SSH / 文件等新增插件同等，不再特殊）。
  - **变量写入落笔在 M6 叶子执行器**（工具调用处拆 `target` → 写 `space`）；
    插件框架与具体插件都不碰 `space`/`frame`。
  - **`use_capability` 在插件框架**（框架级工具，不经过具体插件）。

- [x] **T11. 报告泛化**
  结论：
  - 报告 = **引擎基础**（node_type / node_desc / result / timestamp / action_call /
    llm_trace）+ **插件附加**（结构化，由插件决定写入什么）。
  - 插件报告信息**走返回值**（`FunctionResult.report`），引擎落笔——与变量写入同构，
    插件不接触 reporter。
  - reporting 提供**统一结构化接口**（details 容器，按来源/插件分组）：引擎落笔、
    渲染时按来源展示。
  - `page_url` / `screenshot_path` **不再由引擎硬编码**，成为浏览器插件的附加信息。
  - **截图时机**：在 `semantic_graph`（"看页面"）时强制截图并写入报告（浏览器插件产物）；
    M7 遍历器**不再无条件截图**。

- [x] **T12. Condition 泛化**
  结论：Condition 与 Action **共用能力机制**（能力概览 + `use_capability` + 函数调用 +
  懒装配），唯一区别是最终输出——真/假（Condition）vs 成功/失败（Action），
  `parse_final_decision` 按 `node_type` 解析。Condition 可用任意能力判断
  （浏览器 / 计算 / 文件 / SSH）。**Condition 不写变量**（只出真/假给控制流）。

- [x] **T13. 一个 Action 调多工具 / 多返回值**
  结论：方案 1（T9）下天然解决——**每个产出型工具调用自带 `output_param`（target）**，
  多个工具调用各自把返回值写各自目标变量，不依赖顺序/命名匹配。非产出型工具无 target。

- [x] **T14. 插件依赖的第三方包**
  结论：
  - **预置插件**（工具开发期已确定）可依赖三方库，**提前安装**到引擎环境（conda `autobranch`）。
  - **用户自定义插件**（单文件）**仅用 Python 标准库**，**不支持 pip 三方库**（不可预知，
    暂不支持）。
  - 引擎**不做依赖自动识别/安装**（`import` ↔ `pip` 名映射不健壮）。

- [x] **T15. 插件函数的重试/确定性语义**
  结论：**不加"幂等/重试"声明**，由插件开发者负责；行为树的 `Retry` 节点单纯做重试
  （是否安全重试由开发者/行为树作者自行判断）。

> 结论回填格式：每一项确认后，把 `[ ]` 改 `[x]` 并在其下补一句结论（或指向正文章节）。

## 9. 前端插件管理（新增）

前端新增「插件管理」，把插件开发从"改文件 + 重启"变为"Web 编辑 + 即时生效"。

### 9.1 页面与功能

- **插件列表**：预置（builtin，只读，徽标"预置"）+ 自定义（custom，可编辑，徽标"自定义"）。
- **新增 / 编辑 / 删除**自定义插件；预置插件只读。
- **代码编辑器**（Python）。

### 9.2 编辑器

- **CodeMirror 6**：Python 语法高亮 + 括号/缩进/基础补全。
- 不做完整 LSP（避免引入 Pyright 服务的重量）。

### 9.3 校验

- **保存时后端校验**：`ast` 语法 + 约束（仅标准库、不 import 其他插件/common/三方库、
  `@engine_function` 格式）。
- 前端**详尽提示**：行号 + 错误信息 + 约束说明。

### 9.4 插件数据模型（DB）

```
plugin 表:
  name / kind(builtin|custom) / description / functions / source / created_at / updated_at
```

- **启动时**扫描 `plugins/` → 初始化/刷新 builtin 记录（只读）。
- **启动后**：builtin 只读；custom 可增删改（源码存 DB）。
- 加载：预置插件 `import`（文件系统）；自定义插件 `compile + exec`（DB 源码）。

### 9.5 删除关联

- 删除插件弹窗**列出引用该插件的关联行为树**（后端扫描行为树的 FunctionCall 节点）。
- 用户决定是否删除；**删除后**行为树里对应 FunctionCall 的 `function` 字段**置空**，
  校验报"悬空引用"（让用户修复）。

### 9.6 后端 API

```
GET    /api/plugins               列出（预置 + 自定义，含 kind）
GET    /api/plugins/{name}        读源码
POST   /api/plugins               新增（自定义）
PUT    /api/plugins/{name}        更新（自定义）
DELETE /api/plugins/{name}        删除（自定义）
POST   /api/plugins/{name}/check  校验（语法 + 约束）
```
